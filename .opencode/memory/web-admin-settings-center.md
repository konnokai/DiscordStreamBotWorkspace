# Web admin settings center

Cross-repo feature adding a `/settings` management UI to the existing `stream-bot.konnokai.me` site.

- Plan: `DiscordStreamNotifyBot/docs/WEB_ADMIN_SETTINGS_PLAN.md`.
- Boundary: Frontend only transports admin DTOs; Backend handles Discord identity and guild authorization; the Notifier shard that holds the guild is the sole entry for business rules, Discord objects, and MySQL mutation. Backend must not write Bot settings tables.
- Reuse existing Vue SPA, ASP.NET Backend, MySQL, Redis, and Notifier; no new framework or service.
- Initial first version scope: common settings (locale, global notice channel, verification log channel); YouTube notifications (source, stream/video channels, messages, create event); Twitch notifications (source, channel, start/end/change messages); TwitCasting notifications (source, channel, start message). It did not modify crawler, YouTube member verification, or Twitch subscription verification settings, but had to expose detection capability and must not mark notifications as working when the crawler is disabled.
- Follow-up plan `docs/WEB_ADMIN_CRAWLER_VERIFICATION_PLAN.md` expands the center with crawler management and verification management. New contract actions include `youtube-crawler.add/remove`, `twitch-crawler.add/remove`, `twitcasting-crawler.add/remove`, `youtube-verification.upsert/remove`, `youtube-verification.set-probe-video`, `youtube-verification.use-automatic-probe`, and `twitch-verification.upsert/remove`; contract sections `crawlers` and `verification` plus `roles`. TwitCasting default crawler limit stays 2, matching Slash. Crawler thresholds: Twitch 200 (or actor is the same broadcaster via OAuth bypass), TwitCasting 500, YouTube verification 250; platform caps follow GuildConfig. Implementation reuses existing platform services, role services, guild locks, DB primary keys, and Redis reconcile; no new registry, interface, or schema. Crawler eligibility threshold for general guilds is 500 members; Twitch verification upsert accepts a numeric canonical broadcaster ID directly instead of treating it as a login. Frontend maps stable crawler/verification error codes to fixed Traditional Chinese messages, preserves `reply.code`, and never retries an `unknown` result.
- Mutation model: one explicit target state per submission; no full config batch overwrite; no toggle commands, booleans are explicit `true`/`false`.
- Contract: Discord snowflakes are decimal strings. Envelope fields: `contractVersion`, `correlationId`, `guildId`, `actorUserId`, `action`, `payload`. First actions: `guild.set-locale`, `guild.set-global-notice-channel`, `guild.set-verification-log-channel`, `youtube-notification.upsert/remove`, `twitch-notification.upsert/remove`, `twitcasting-notification.upsert/remove`.
- Redis channels: `admin:settings:snapshot:request`, `admin:settings:command:request`, `admin:settings:reply:{correlationId}`, and guild snapshot hash `cluster:stats:guild_snapshot`.
- Status as of 2026-11 transcripts: implemented across Bot, Backend, and Frontend; automated checks passed (Bot build 0 warnings/errors, 614 tests passed/36 skipped; Backend 75 tests passed; Frontend build/lint/style/Prettier passed), but formal Discord/Redis/MySQL/multi-shard and Chrome desktop/mobile acceptance remained unverified. No commit/push at that point.
- Backend now rejects snapshots missing `crawlers`/`verification`; Frontend preserves mutation `code` for specific rejection messages. Slash crawler/verification commands delegate to the same domain services used by the web center.
